# Beryllium — роадмап

Путь от пустого репозитория до релиза 1.0. Каждый пункт — отдельный небольшой шаг, который можно закрыть одним коммитом или PR. Номера шагов (`3.4`) удобно указывать в коммитах и issue.

**Обозначения:** `[ ]` — не сделано, `[x]` — сделано, 🍎 / 🐧 / 🪟 — шаг относится только к macOS / Linux / Windows.

**Вехи:**

| Веха | Фазы | Результат |
|---|---|---|
| **M1 — «Работает в терминале»** | 0–7 | Демон и CLI на всех трёх ОС: подписка, подключение, TUN, переживает сон |
| **M2 — «Альфа»** (`v0.1.0`) | 8–10 | TUI и GUI, установщики, первые пользователи |
| **M3 — «Бета»** (`v0.5.0`) | 11–13 | Автообновление, kill switch, мульти-ядро с автовыбором, стабильность |
| **M4 — «Релиз»** (`v1.0.0`) | 14–15 | Полное тестирование, документация, публичный релиз |

## Фаза 7. Надёжность: сон, смена сети, watchdog ⭐ (главная причина проекта)

### 7A. Health-check и watchdog
- [ ] 7.1 URL-тест через туннель (`generate_204` на нескольких хостах, засчитывается, если ответил хотя бы один)
- [ ] 7.2 Watchdog с периодом 20–30 с (настраивается); после 2–3 неудач подряд запускается восстановление
- [ ] 7.3 Машина состояний соединения: `Disconnected → Connecting → Connected → Degraded → Recovering → Connected | Failed`, все переходы транслируются в `WatchStatus`
- [ ] 7.4 Лестница восстановления: сбросить соединения ядра → перезапустить ядро → сменить сервер (урлтест по группе) → сменить ядро → `Failed` с уведомлением
- [ ] 7.5 Backoff и ограничение частоты восстановлений, чтобы не уйти в бесконечный цикл

### 7B. Сон и пробуждение
- [ ] 7.6 🍎 `IORegisterForSystemPower` через cgo: `WillSleep` (успеть подтвердить и закрыть соединения), `HasPoweredOn`
- [ ] 7.7 🍎 распознавание DarkWake / Power Nap: не устраивать полное восстановление на каждое полупробуждение
- [ ] 7.8 🐧 сигнал `PrepareForSleep` от systemd-logind по D-Bus (`godbus`) плюс inhibitor lock типа `delay`, чтобы успеть закрыть соединения до сна
- [ ] 7.9 🪟 `RegisterSuspendResumeNotification` / `PBT_APMRESUMEAUTOMATIC`
- [ ] 7.10 После пробуждения **сначала ждать готовности сети**: есть default route, интерфейс активен, DNS резолвит (таймаут ~30 с), и только потом восстанавливаться
- [ ] 7.11 Последовательность после пробуждения: сбросить соединения → перечитать default interface → сбросить DNS-кеш (🍎 `dscacheutil -flushcache` + HUP `mDNSResponder`, 🪟 `ipconfig /flushdns`, 🐧 `resolvectl flush-caches`) → health-check

### 7C. Смена сети
- [ ] 7.12 🍎 `SCDynamicStore` (или route socket) для смены primary interface и DNS
- [ ] 7.13 🐧 netlink (`vishvananda/netlink`): изменения маршрутов и адресов
- [ ] 7.14 🪟 `NotifyIpInterfaceChange` / `NotifyRouteChange2`
- [ ] 7.15 Debounce событий сети (~1–2 с), затем тот же сценарий, что после пробуждения
- [ ] 7.16 Captive portal: распознать (нет интернета даже напрямую) и не перебирать серверы впустую. Показать уведомление «Нужна авторизация в сети Wi-Fi»

### 7D. Проверка надёжности
- [ ] 7.17 Скрытая отладочная команда `beryl debug simulate sleep|wake|netchange`: прогоняет сценарии без реального сна
- [ ] 7.18 Unit-тесты машины состояний с фейковыми часами и фейковым ядром
- [ ] 7.19 Ручной чек-лист 🍎: короткий сон (1 мин), долгий сон (ночь), сон + смена Wi-Fi, закрыть крышку → открыть на другой сети, хотспот с телефона. Каждый сценарий ×10, цель — 0 обрывов без восстановления
- [ ] 7.20 Soak-тест: 72 часа непрерывной работы с периодическим сном (`pmset sleepnow` по cron) и логом времени восстановления
- [ ] 7.21 Метрика в `Status`: число восстановлений, последняя причина, время восстановления (для поиска проблем у пользователей)

**Готово, когда:** чек-лист 7.19 проходит на маке, восстановление после пробуждения занимает < 5 с. **Это веха M1.**
